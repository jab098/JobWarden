# Task 13 Application Tracker Review

**Branch:** `codex/task-13-application-tracker`

**Base:** `main` at `72336a3` (Task 17 roadmap addition, after Task 12 publication)

**Review status:** independent six-angle review complete (two further angles were re-verified directly after an environment interruption); all findings remediated test-first at `HEAD` with a clean re-run of the full gate.

## Outcome

Task 13 implements the application tracker for manual external applications. A pure domain module (`packages/domain/src/applications.ts`) owns the eight-stage vocabulary (applied, screening, interviewing, offer, accepted, rejected, withdrawn, archived), the explicit transition map (acceptance requires an observed offer; archiving is always the closing move; the only reverse edge is the explicit audited re-open `archived → applied`, so a terminal mis-click never forces history deletion), deterministic next-action due classification over ISO dates with Europe/London as the product calendar, and insights: stage counts, audited funnel reach, follow-up buckets, and an outcome split where silence is reported as "no stage change for 14+ days" — never converted into rejection or invented recruiter activity.

Migration `202607190003_application_tracker.sql` adds forced-RLS `career_applications` (one row per owner and job; bounded next action ≤200 chars, notes ≤2000 chars, due date) and the append-only `career_application_events` audit table (owner-only select; no authenticated write path exists, so events cannot be forged or rewritten). Four owner-fenced security-definer RPCs take the per-owner generation mutex first: `track_career_application` (idempotent; job must exist; writes the creation event), `transition_career_application` (validates the SQL transition map — kept in lockstep with the domain map by a repository test — and appends the audit event), `update_career_application_plan`, and `delete_career_application`. `delete_career_profile_data` now also erases applications and their audit trail; the events table carries indexes for the RLS owner filter and the application cascade. pgTAP file 014 adds 26 assertions; the static verifier enforces 13 migrations and 27 forced-RLS tables.

The web layer (`apps/web/src/lib/applications/`) mirrors the established repository split with a pure `buildApplicationsResult` shared by the fictional development fixtures and the caller-bound Supabase implementation (parallel application + event reads, sanitised errors, RPC-only mutations). `/applications` provides a URL-backed list and board: the list has stage badges, accessible "Move to" selects offering only legal transitions, next-action/due/notes forms in a disclosure, and two-step delete confirmation; the board groups open stages plus one Closed column and scrolls horizontally inside its own container with the same accessible controls (no drag-and-drop). The insights panel shows funnel reach, follow-up buckets, and the honest outcome split with explicit copy that JobWarden never contacts recruiters. Tracking starts from the job detail page ("Track my application" — recording what the user did on the employer's site), and the control is tracked-aware, pointing an already-tracked job at `/applications` instead. An application whose listing later closes keeps rendering with an honest "Listing no longer available" card (the RLS-hidden job embed is nullable), so one closed advert can never take the page down. Applications joined the desktop rail and mobile navigation.

## Independent review remediation

The review waves surfaced and remediation resolved, test-first: the closed-listing whole-page failure (nullable `jobs` embed with a graceful card), the missing recovery path from terminal stages (explicit audited `archived → applied` re-open in the domain map, the SQL pair list, and the UI), UTC/local date drift (due dates formatted in UTC; "today" for due and quiet arithmetic derived in Europe/London via `londonIsoDate`), missing indexes on `career_application_events`, a stateless track button (now tracked-aware) plus wasted `/jobs` revalidation (now targeted at job detail pages), and the quiet-bucket label (now "No stage change for 14+ days" to state its exact semantics). Accepted, recorded observations: cross-feature duplication of the job-row schema, mutation origin context, and repository-factory boilerplate follows the existing codebase convention and is deferred as cleanup; funnel reach assumes RPC-written audit events, which is guaranteed because no other write path exists.
