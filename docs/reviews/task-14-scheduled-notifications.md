# Task 14 Scheduled Updates and Notifications Review

**Branch:** `codex/task-14-scheduled-notifications`

**Base:** `main` at `47fa8f4` (Task 13 publication record)

**Review status:** independent review complete; all findings remediated at `HEAD` with a clean re-run of the full gate.

## Outcome

Task 14 computes new Target Feed matches after each shared weekday ingestion slot and sends at most one digest per owner per slot, only when a genuinely new job/profile match exists.

`packages/domain/src/notifications.ts` is pure and deterministic. `londonSlotKey` resolves an instant to an hour-resolution `Europe/London` slot (`2026-07-20T09`) or null outside the weekday 09/12/15/18 cadence, so a cron entry that fires a few minutes after ingestion still lands on the right slot and a misfire outside the cadence is a no-op rather than an unexpected send. `selectNewMatches` runs the existing `applyEligibilityGate` and `scoreJobForProfile` rather than reimplementing either, so a digest can never disagree with the feed it links to; it drops already-announced `(searchProfileId, jobId)` pairs, returns one announcement per matching pair, and lists each job once under its highest-scoring new profile. `buildDigestMessage` renders subject, plain text, and HTML from `DigestJobSummary`, a type that carries only job title, employer, location, and profile name — career evidence is structurally absent, so "no CV text in the payload" is enforced by the type rather than by reviewer care. Provider-supplied job text is HTML-escaped, because an advert is untrusted content in an email exactly as it is on a page.

Migration `202607190004_scheduled_notifications.sql` adds three forced-RLS tables: `career_notification_settings` (owner-keyed, `channel_enabled` defaults false, unique unsubscribe token), the pair-scoped `career_notification_announcements` deduplication ledger, and `career_notification_deliveries`, which is simultaneously the user-visible delivery status and the auditable free-tier counter — there is no second ledger that could disagree with it. Unique `(owner_id, slot_key)` makes a repeated invocation a no-op. `begin_notification_digest` decides and records the slot outcome atomically before anything is sent, counting `pending` alongside `sent` so an in-flight send cannot race past the ceiling; `finish_notification_digest` moves a claimed row to `sent` or `failed` and records announcements **only** on success, so a provider failure never suppresses the next slot's digest. `set_career_notification_settings` is owner-fenced behind the generation mutex; `unsubscribe_career_notifications` is deliberately `anon`-executable because an unsubscribe link has to work from an email client, and is safe because a token is its only input, it returns nothing but whether a row matched, and it can only clear a flag. `delete_career_profile_data` now erases all three tables. pgTAP file 015 adds 34 assertions; the static verifier enforces 14 migrations and 30 forced-RLS tables and gained a reviewed allowlist so no _other_ definer function can quietly become anon-executable.

`supabase/functions/send-digests/` mirrors the reviewed `ingest-jobs` shape (constant-time bearer check, body-size cap, 120-second invocation deadline, `verify_jwt = false`). It reads the 200-job candidate window **once per invocation** and scores it for every recipient, and makes no source request at all, so the digest path cannot create per-user source cost. Career evidence reaches it without the excerpt column: the database projection omits CV prose entirely. Without `RESEND_API_KEY` the function reports `delivery_unconfigured`, claims no slot, and sends nothing.

Resend is reached over its documented HTTP API rather than the npm SDK, so no dependency was added to the workspace. The guardrail's global ban is replaced by an exact-path allowlist covering only the adapter, its test, and the function's deployment entry point; the guard now also reads the whole `supabase/functions` tree, and executable tests prove it rejects a planted reference in a client component, a web server module, a workspace package, the notification handler itself, and another Edge Function.

The web layer adds `/profile` notification settings (channel toggle, cadence explanation, honest per-slot delivery status), a real per-search notification control replacing the hardcoded `notificationsEnabled: false` and the literal `notifications off` label, and the public `/unsubscribe` token page.

## Independent review remediation

Five findings were surfaced and fixed at `HEAD`:

1. **Announcement bound below the runtime's own worst case (important).** `finish_notification_digest` capped announcements at 2,000, but an owner's first digest can legitimately produce `MAX_CANDIDATE_JOBS × MAX_SEARCHES_PER_OWNER` = 5,000 pairs. Above the cap the email would already have been sent, the recording would be rejected, the delivery row would stay `pending`, and the same matches would be re-sent at the next slot — a direct violation of the deduplication criterion. The bound is now 5,000 with the arithmetic named in the SQL, a domain test that makes the candidates × searches product explicit, a verifier fragment, and two pgTAP assertions.
2. **One owner's data could take down every owner's digest (important).** `list_pending_notification_digests` returned unbounded per-owner searches and evidence while the runtime's schema capped them at 25 and 250. An owner with 26 notifying searches would fail validation, failing the whole `listRecipients` read and returning 503 for everyone. Both projections are now bounded in SQL at the same numbers, so that owner degrades to their oldest searches instead.
3. **Duplicate career-snapshot read on every profile page render (efficiency).** The notifications repository re-fetched the full career snapshot only to derive the notifying profile names, which the page had already loaded. The repository now reads only its own two tables and returns `NotificationChannelState`; the page composes the names it already holds. A regression test asserts the repository touches no other table.
4. **Dead abort signal (correctness).** The handler created an `AbortController` it never aborted and passed its signal to every send. It now passes a signal carrying the remaining invocation budget, so a send started near the deadline is cut off rather than running past it.
5. **Ambiguous sender parsing (correctness, caught by its own test).** The first `NOTIFICATION_SENDER_ADDRESS` regex parsed the bare address `digests@jobwarden.example` as display name `d` plus address `igests@…`. The two accepted forms are now matched explicitly.

Two further corrections came out of the gate itself: fixture cron secrets were rewritten in the repository's existing `"cron-fixture-".repeat(3)` style after Gitleaks flagged hex-like literals, and `_shared/supabase.ts` now takes a two-field `ServiceRoleCredentials` type instead of importing `ingest-jobs`' full runtime contract, which had been dragging the ingestion package into the new function's Deno graph.

Accepted, recorded observations: a database failure occurring precisely between a successful send and its recording leaves a `pending` row and can re-announce those matches at the next slot. This is the inherent at-least-once boundary of send-then-record; the alternative ordering would silently swallow matches on failure instead, which is worse for the product. Slot uniqueness prevents duplication _within_ a slot, and the window is documented in the operations guide. Cross-feature duplication of mutation-origin context and repository-factory boilerplate follows the existing codebase convention and is deferred as cleanup.
