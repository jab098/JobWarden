The `on delete set null` shows deletion was intended to work and leave the record unattributed; the trigger defeats that intent. The defect stayed hidden because the outcome was `excluded` rather than `quarantined`: `supabase/functions/ingest-jobs/handler.ts` skips both identically, nothing is persisted, and the source run record counts only `receivedCount` and `eligibleCount`, so a source discarding 95% of its stock read as a source without much UK content. `classifyUkEligibility` also returns on a `non_uk` location before reading the description, so "based in our Salford office in the UK" could not rescue it.

What changed is the consequence of an unrecognised label, not the test for one. The first implementation made unrecognised labels neutral and moved the entire burden onto a denylist of foreign places; independent review rejected it, and was right to, because publication then depended on the _absence_ of a denylist entry. Three verified ways through it: `isForeignLabel` matched on trim-and-lowercase while the UK side stripped punctuation, so 25 of 28 punctuated forms published including `London, Ont.`, `Manchester, N.H.` and `Bath, U.S.A.`; four subdivisions were missing, so `Bangor, ME`, `Newport, OR` and `Brighton, Victoria` published; and 135 of 136 probed qualifiers were absent entirely, including all New Zealand regions, all Irish counties and some sixty countries, because a denylist of foreign places cannot be enumerated. The remediation restores the original allowlist test and changes only what happens when it fails, to `ambiguous`, which `normalise.ts` already routes to `quarantined`. Publication now requires every label to be positively recognised, so `London, Ont.` is refused because `ont.` is unknown rather than because anyone remembered to list it. Recognition widened to match: exact per-label lookup against the 230-place gazetteer (deliberately not `resolveUkPlaces`, which matches contained names and reads "New York City" as York), 160 administrative areas derived from the dataset's own `county` and `region` fields with multi-name values indexed part-wise, and a hand list of 47 ceremonial counties, because the dataset stores the unitary authority — Leeds's county is "Leeds" — and cannot supply `West Yorkshire`. Of the 27-city allowlist, 25 became redundant and were deleted; `Derry` and `Newcastle` remain because the gazetteer spells them `Londonderry` and `Newcastle upon Tyne`. The denylist survives only as defence in depth, to answer `non_uk` where the answer is known rather than clog the review queue, and because it is no longer load-bearing its entries are omitted rather than risked: `washington` was removed (a town of 67,000 in Tyne and Wear that the first implementation excluded even when the advert said England), `victoria` was never added (it names a district of London), and of the subdivision codes only those that are not also UK postcode areas are included, so `Derby, DE` and `Bangor, ME` quarantine as unrecognised instead of being discarded as foreign.

One limit is documented rather than asserted away: a location whose every label is a real UK place name cannot be told from a UK one by name alone. `Lincoln, Canterbury` and `Oxford, Canterbury`, both real New Zealand towns, publish because Canterbury is also a city in Kent, as does `Newport, Manchester`, a parish in Jamaica. Naming a country closes it — `Lincoln, Canterbury, New Zealand` is `non_uk` — so the exposure is a two-label advert naming no country. Closing it properly would require qualifier positions to be administrative areas rather than any UK place name, which was measured to cost `London, Canary Wharf` and `Manchester, Salford Quays`. A behaviour change worth recording: because a `non_uk` location outcome is now strictly rarer, a location such as `Amsterdam` paired with a description saying "Applicants must be based in the UK" now publishes where it was previously excluded on the location alone; that follows the specification, since explicit UK eligibility evidence in the advert body is what the description rules exist to read, but it was not an intended part of this change.

Task 25c makes ingestion say why it discarded an advert. `supabase/functions/ingest-jobs/handler.ts` skipped every non-eligible normalisation outcome with a single `continue`, nothing was persisted, and `ingestion_source_runs` counted only `received_count` and `eligible_count`, so a source discarding 95% of its stock was indistinguishable from a source without much UK content. Independent review returned APPROVED after one round of CHANGES REQUIRED, and the finding was a live security regression rather than anything in the feature. The `finish_source_ingestion` body was extracted from `202607180003` by script and patched rather than hand-written, which is where review was told to look hardest; a line-by-line diff found it faithful, with every branch, advisory lock, omission path, and audit insert intact. The defect was one rung above it. This is the repository's first `drop function`: every other migration uses `create or replace`, which preserves a function's privileges, while drop plus create starts from PostgreSQL's default ACL granting EXECUTE to PUBLIC. Both existing `revoke ... from public, anon, authenticated` statements name the eleven-argument signature this migration deletes, so the fifteen-argument replacement — a security-definer function that bypasses RLS to close live jobs and append audit records — was left reachable by any holder of the anon key. It was silent in both directions available to it: `service_role` belongs to PUBLIC, so ingestion would have kept working and nothing would have failed at runtime, and `verify-supabase-foundation.mjs` matched its revoke rule on the function name with any argument list, so the stale eleven-argument revoke satisfied the check for a function that no longer existed. The guardrail certified the hole. The migration now revokes and grants explicitly; the verifier compares each revoke's offset against the last `drop function` for that name and anchors the name to its opening parenthesis, closing a second pre-existing route in which a longer function name satisfied a shorter one (`upsert_ingested_jobs` was masking `upsert_ingested_job`); and it asserts that `requiredMigrationFiles` stays chronological, which the offset comparison silently depends on. Each protection was checked by removing it and confirming the verifier fails by name. pgTAP file `022` (16 assertions) adds direct `has_function_privilege` assertions that `anon` and `authenticated` cannot execute the RPC, which the file had omitted while asserting `is_definer`.

Task 27 closes the reported onboarding hydration defect without a code fix, because there was no defect. The report held that `OnboardingFlow` attached no React fiber, that `useActionState`, `ActionFeedback` and every client effect inside it were inert, and that the buttons worked only through progressive enhancement. It was tested at `9d2b49b` — the commit the report cited as its own proof — in a detached worktree running its own dev server, and again on `main`. Both hydrate. The root cause is the measurement rather than the code: counting `__reactFiber$` properties is a mechanism check that produces false negatives easily, because most elements on a page legitimately carry no fiber and `<head>`, `<link>` and `<script>` — which never do — sort first in `document.querySelectorAll("*")`. The report's supporting evidence pointed the same way the whole time; client chunks returning 200 with a clean console is what a working page looks like, not a puzzle.

Three checks disprove it. Fibers and props attach to `main`, both submit buttons, and both `Enter` divs, and the only elements without them are `<head>`, `<link>` and `<script>`. `sessionStorage["jobwarden:seen-surfaces"]` contains `onboarding-cv-cv`, the key of the `Enter` nested inside the flow, so a client effect within the subtree ran — the exact observable this task's acceptance named. And with a value written to `window`, submitting a step advanced "Your CV" to "Where you want to go" with that value intact and the navigation-entry count still at one; a progressively-enhanced POST unloads the document and would have destroyed both, so React had intercepted the submit. `seenSurfaces` then gained `onboarding-aspiration-aspirations`, showing the next step's effect ran in place without a navigation.

The deliverable is therefore the regression test the flow never had. `onboarding-ui.test.tsx` renders the flow through `renderToString`, hydrates that markup with `hydrateRoot`, and asserts both that the entrance recorded its surface key and that `onRecoverableError` stayed silent — outcome rather than mechanism, per `docs/standards/frontend-traps.md`. Both assertions were mutation-checked: emptying the `Enter` effect fails the first, and a genuine server/client divergence fails the second with React's own hydration-mismatch diff. Two earlier attempts at that second mutation were invalid rather than informative, and are recorded here because each is a trap for the next person writing a hydration test in this repo — a `typeof window` branch does not diverge under jsdom, where `window` exists during `renderToString` too, and a module-level counter does not diverge in a full-file run, because twenty-eight earlier tests in the same file render the component first and exhaust it. Only an isolated run of the mutated test diverges. `"use client"` was deliberately left untested: a React hook in a server component fails the production build `pnpm verify` already runs, so the compiler is that regression test. `docs/standards/frontend-traps.md` has been corrected, since it had told the next agent that client behaviour inside onboarding was dead code and to check before building on it. Two causes, and they must not be conflated. Most aborts are fixture drift, which is bookkeeping: 001 dies on `null value in column "deduplication_key" of relation "jobs"`, a `not null` column a later migration added to a fixture written before it existed, and 022 asserts the forced-RLS table count is 32 when two tables have since taken it to 34. The defect this exposed is the part worth remembering. Route entrances animated on reload and not on navigation, which reads as a navigation bug and is not one. The App Router nests `layout → template → Suspense(loading.tsx) → page`, so `template.tsx` — and therefore `Enter` — sits above the Suspense boundary, and every protected route has a `loading.tsx`. On a client-side navigation the wrapper mounted with the loading skeleton, spent the entrance on it, and the real content then swapped in underneath without remounting, so the page a reader actually waited for arrived with no animation at all. A reload has no skeleton, which is why it looked fine. The fix animates the wrapper's child rather than the wrapper, because the skeleton-to-content swap is a genuinely new DOM node; that is one selector rather than edits to seventeen pages. It was found by using the product, not by a test, and it slipped through because the earlier check confirmed the _class_ was applied rather than that the animation _ran_ — the exact trap `docs/standards/frontend-traps.md` already documents, walked into by the person maintaining that file.

Skeletons no longer interrupt the entrance. A skeleton does not run it, and is held invisible for `--delay-skeleton: 260ms`, so a navigation resolving faster than that shows no loading state at all: the previous page holds, then the real content arrives with its own entrance. The delay is expressed as a backwards animation fill rather than a visibility toggle so nothing leaves the accessibility tree and `role="status"` still announces immediately. All ten loading roots carry `data-skeleton`; two of them initially passed it to a React component rather than a DOM node, where it would have silently done nothing, so the attribute moved onto `JobsLoadingView`'s own root.
